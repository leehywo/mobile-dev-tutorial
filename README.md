# 모바일 앱 개발 튜토리얼

> **React/JavaScript 개발자**가 모바일(그리고 게임) 개발로 확장하기 위한 한국어 튜토리얼 시리즈.
> 모든 문서가 같은 교수법을 씁니다 — **아는 것(JS/React)과 1:1로 비교**하며 배우고,
> **동일한 샘플 앱을 단계별로 완성**하며 트랙 간 차이를 몸으로 익힙니다.

## 튜토리얼 트랙

| 트랙 | 문서 | 기술 스택 | 이런 사람에게 |
|------|------|----------|--------------|
| 🤖 **Android** | [android-kotlin-compose.md](./android-kotlin-compose.md) | Kotlin + Jetpack Compose | Mac 없이 시작 가능. 출시 비용 저렴($25 1회), 심사 빠름 |
| 🍎 **iOS** | [ios-swift-swiftui.md](./ios-swift-swiftui.md) | Swift + SwiftUI | **Mac 필수**. 수익성·UX 완성도 높고 고유 기능(Live Activity 등)이 강력 |
| 🎮 **Unity** | [react-to-unity.md](./react-to-unity.md) | C# + Unity 6 (UI Toolkit / UGUI) | 게임·인터랙티브 콘텐츠·AR/VR이 목표 |

> **크로스플랫폼(React Native/Flutter) 트랙은 이 시리즈에서 다루지 않습니다.** 이유와 대안은
> 아래 [크로스플랫폼은 어디로 갔나](#크로스플랫폼은-어디로-갔나) 참고.

## 트랙 선택 가이드

```
만들려는 게 무엇인가요?

게임 / 3D / AR·VR / 물리·애니메이션 중심 콘텐츠
  → 🎮 Unity 트랙 (고민할 것 없이 이것)

폼·리스트·네비게이션 중심의 "일반 앱"
  ├─ Mac이 없다 / 안드로이드를 쓴다 / 빨리 스토어에 올려보고 싶다
  │    → 🤖 Android 트랙 (계정 $25 1회, 심사가 빠릅니다)
  └─ Mac이 있다 / 아이폰을 쓴다 / 구독·인앱결제로 돈을 벌 계획이다
       → 🍎 iOS 트랙

아직 모르겠다
  → **자기가 매일 쓰는 폰의 트랙**부터 하세요. 만든 걸 바로 자기 폰에 깔아
    며칠 써보는 것이 학습 속도를 가장 크게 좌우합니다. 시뮬레이터에서만
    돌린 앱은 끝까지 안 만들게 됩니다.
```

### 두 네이티브 트랙 비교

| | 🤖 Android | 🍎 iOS |
|---|---|---|
| 개발 OS | Windows / macOS / Linux | **macOS만** |
| 계정 비용 | $25 (1회) | $99/년 |
| 심사 | 자동 위주, 보통 수시간~1일 | **사람이 직접 심사**, 1~3일 + 리젝 가능성 |
| 첫 출시 난이도 | 중 (신규 개인 계정은 테스터 요건 있음) | 중~상 (심사 가이드라인) |
| 언어 함정 | 적음 (`val`/`var`가 JS와 감각 동일) | `let` = JS의 `const` ⚠️ |
| 상태 관리 | ViewModel + StateFlow | `@Observable` + 프로퍼티 래퍼 |
| 화면 회전 | Activity 재생성 → 상태 소실 주의 | 상태 유지됨 (편함) |
| 고유 기능 ROI | App Widget (Glance) | Live Activity / Dynamic Island |

> **둘 다 할 계획이라면**: 한쪽을 끝까지 한 뒤 다른 쪽을 보세요. 두 번째 트랙은
> 개념이 이미 머리에 있어서 보통 절반 이하 시간(15~20시간)이면 됩니다.
> 각 문서 PART 5 끝의 **대조표 부록**이 개념 매핑을 정리해둡니다.

## 공통 학습 설계

세 트랙 모두 같은 구조로 진행됩니다. 두 번째 트랙부터는 "아, 그거"의 연속이라 훨씬 빠릅니다.

```
PART 0  개발 환경 세팅 (설치 확인 체크리스트, 빌드 도구 개념)
PART 1  언어 문법 — JS/TS와 나란히 비교 (Kotlin / Swift / C#)
PART 2  매핑 치트시트 — useState는 여기서 뭐지? 를 표로
PART 3  샘플 앱 단계별 완성
         카운터 → 상태관리 → 할 일 목록 → 날씨 앱(API) → 메모 앱(DB·이미지·테마)
PART 4  실전 — 디버깅·권한·인앱결제/구독·릴리즈·테스트·접근성·성능·스토어 출시·지뢰 모음
PART 5  학습 로드맵 (Claude 어시스트 Fast-track 포함) + 다른 트랙 대조표
```

## 환경 요구사항 요약

| | 🤖 Android | 🍎 iOS | 🎮 Unity |
|---|---|---|---|
| 개발 OS | 모든 OS | **macOS 필수** | 모든 OS (iOS 빌드는 macOS) |
| 도구 | Android Studio | Xcode | Unity Hub |
| 디스크 여유 | ~20GB | ~40GB | ~20GB |
| 유료 계정 | Google Play $25(1회) | Apple $99/년 | 출시 스토어에 따라 (Unity Personal 무료) |

> ⚡ 각 문서 상단의 **Claude 어시스트 Fast-track**을 활용하면 네이티브 트랙당 6~9시간,
> AI 없이 전통적으로 학습하면 트랙당 30~45시간 정도입니다.

## 출시 직전 체크리스트 (2026 기준)

튜토리얼을 끝내고 **실제로 스토어에 올릴 때** 걸려 넘어지는 것들입니다. 코드 문제가 아니라
정책·설정 문제라서 검색으로도 잘 안 나오고, 대부분 제출 후에야 알게 됩니다.

**🤖 Google Play**
- [ ] **`targetSdk`가 최신 요구 버전인가.** Play는 매년 8월 말에 상향 마감이 있고, 넘기면
      **기존 앱의 업데이트 자체가 막힙니다.** 라이브 앱이 있다면 매년 이 날짜를 달력에 넣으세요.
- [ ] **릴리즈 AAB를 실제로 설치해봤는가.** 빌드 성공 ≠ 실행 성공입니다. `bundletool`로
      universal APK를 뽑아 에뮬레이터에 콜드런치해보면 R8/ProGuard가 지운 클래스 때문에
      나는 크래시를 출시 전에 잡습니다.
- [ ] **업로드 키를 백업했는가.** 키스토어 비밀번호를 잃어버리면 업로드 키 재설정을
      요청해야 하고 며칠이 걸립니다(앱이 죽지는 않습니다 — Play 앱 서명이 최종 서명을 대신합니다).
- [ ] 데이터 보안(Data Safety) 설문이 실제 코드와 일치하는가. 광고 SDK를 뺐다면 설문도 바꿔야 합니다.

**🍎 App Store**
- [ ] **개인정보 라벨이 실제 코드와 일치하는가.** 라벨에 "추적"을 선언했다면 **ATT 팝업 코드가
      실제로 있어야** 합니다. 문구만 있고 코드가 없으면 5.1.2로 리젝됩니다.
- [ ] **구독·인앱결제 앱은 복원 버튼이 필수.** 그리고 복원은 **로컬 조회를 먼저** 하세요.
      먼저 계정 인증을 띄우면 이미 구매한 사람에게 불필요한 암호창이 뜹니다.
- [ ] **첫 비소모성 인앱 상품은 앱 버전과 함께 제출**해야 승인됩니다. 버전만 제출하면
      앱만 라이브가 되고 상품은 미승인 상태로 남아 **결제가 안 되는 앱**이 됩니다.
- [ ] 스크린샷·설명문이 앱의 실제 기능과 일치하는가. 없는 기능을 파는 문구는 리젝 사유입니다.

**공통**
- [ ] **스토어에 등록한 상품이 앱이 조회하는 상품 ID와 정확히 같은가.** 페이월 코드가 완성돼도
      상품이 없거나 ID가 다르면 **가격이 안 뜨고 아무도 결제할 수 없습니다.** 출시 전에
      실기기에서 페이월을 열어 가격이 실제로 보이는지 확인하세요.
- [ ] 다국어를 지원한다면 **앱 문자열과 스토어 리스팅을 한 세트로** 올렸는가. 앱만 32개 언어여도
      스토어 페이지가 영어면 그 언어권 사용자는 검색에서 찾지 못합니다.
- [ ] 개인정보처리방침 URL이 **지금 이 순간 200으로 열리는가.** 404 링크는 리젝 사유입니다.

## 크로스플랫폼은 어디로 갔나

초판에는 React Native(Expo) 트랙이 있었지만, 이 시리즈는 **네이티브 2종 + Unity**로 좁혔습니다.

- 이 시리즈의 목적은 "가장 빨리 앱 하나 내기"가 아니라 **플랫폼을 이해하는 것**입니다.
  위젯·백그라운드 동작·결제·알림처럼 실제로 앱의 성패를 가르는 부분은 결국 각 OS의 규칙이고,
  크로스플랫폼으로 시작하면 그 규칙을 **문제가 터진 뒤에** 배우게 됩니다.
- 유지보수 관점에서도, 튜토리얼이 다루는 범위가 넓어질수록 **모든 트랙을 최신으로 유지하기가
  어렵습니다.** 낡은 크로스플랫폼 문서는 없는 것보다 나쁩니다.
- **RN/Flutter가 나쁜 선택이라는 뜻은 아닙니다.** 팀에 React 인력이 많고 화면 위주의 앱이라면
  여전히 합리적입니다. 다만 그 길은 공식 문서(Expo·React Native·Flutter)가 이 문서보다
  잘 관리합니다 — 거기서 시작하고, OS 고유 기능이 필요해지는 순간 이 시리즈의
  네이티브 트랙으로 돌아오세요. 그때는 이미 절반쯤 아는 상태입니다.
