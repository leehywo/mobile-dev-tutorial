# 21. 코어 루프와 기획서

> **이 장에서 배울 것**
> - MDA 프레임워크로 "재미"를 메커닉·다이내믹·미학 세 층으로 나누어 설명할 수 있다
> - 코어 루프와 메타 루프를 다이어그램으로 그리고, 루프의 약한 고리를 찾는다
> - 레퍼런스 게임을 플레이 기록 템플릿으로 해부해 장르의 재미 요소와 빈틈을 찾는다
> - 훅 한 문장과 1페이지 기획서를 작성하고, MoSCoW로 기능 우선순위를 정한다
> - 그레이박스 프로토타입으로 "검증할 질문 하나"를 확인하는 계획을 세운다
>
> **선수 장**: 기초 트랙 (1·2부를 마쳤다면 더 좋음) · **예상 시간**: 4~6시간 (레퍼런스 플레이 시간 제외) · **코인 러시 진행**: 코인 러시 1페이지 기획서, 레퍼런스 3종 해부표, 기능 우선순위 표, 2주 그레이박스 계획

## 왜 필요한가

20장까지 오면서 코인 러시에는 이벤트로 연결된 체력, ScriptableObject 데이터, 상태 머신, 오브젝트 풀, 쉐이더, 에디터 툴이 생겼습니다. 기술적으로는 꽤 괜찮은 게임입니다. 그런데 지인에게 5분만 해보라고 건네면 이런 장면이 흔합니다.

```
0:00  "오, 움직이네."
1:30  적을 피하며 코인을 줍는다. 레벨업 창에서 아무거나 누른다.
3:00  "근데 이거 뭘 하면 되는 거야?"
4:10  휴대폰을 확인한다.
5:00  "재밌네~" (다시 켜지 않음)
```

코드는 멀쩡합니다. 문제는 **플레이어가 내리는 결정이 없다**는 것입니다. 레벨업 선택지는 어느 것을 골라도 비슷하고, 코인은 줍기만 할 뿐 쓸 곳이 없고, 3분이 지나도 상황이 달라지지 않습니다. 프로그래머 출신 인디의 가장 흔한 실패가 바로 이것, **기술적으로 잘 만든 재미없는 게임**입니다.

이 장부터 3부는 코드보다 문서와 표를 더 많이 만듭니다. 웹 개발에 비유하면, 컴포넌트를 더 짜기 전에 "사용자가 이 화면에서 무엇을 하려는가"를 정의하는 제품 기획 단계입니다. 다만 게임의 "사용자 목표"는 기능 완수가 아니라 **경험**이라서 도구가 조금 다릅니다.

## 개념

### 재미를 분해하는 틀: MDA 프레임워크

MDA는 Robin Hunicke, Marc LeBlanc, Robert Zubek이 2004년 논문으로 정리한 틀입니다. 게임을 세 층으로 나눕니다.

| 층 | 뜻 | 누가 직접 만드는가 | 코인 러시 예 |
|---|---|---|---|
| **M**echanics (메커닉) | 규칙, 수치, 코드. 게임이 "무엇을 하는가" | 개발자 | 이동만 입력, 자동 공격, 적이 코인을 떨굼, 레벨업 3택1 |
| **D**ynamics (다이내믹) | 메커닉이 플레이어 입력과 만나 실행 중에 생기는 행동 패턴 | 아무도 직접 못 만듦 (창발) | 적 무리를 원 그리며 끌고 다니기, 코인 더미로 돌진했다 빠지기 |
| **A**esthetics (미학) | 플레이어가 느끼는 감정적 반응 | 플레이어 | "내가 점점 괴물이 된다"는 쾌감, 아슬아슬한 긴장 |

핵심은 **방향**입니다.

```
개발자의 시점:   Mechanics ──────▶ Dynamics ──────▶ Aesthetics
                (코드로 만든다)     (실행되며 생긴다)    (느낌이 된다)

플레이어의 시점: Aesthetics ──────▶ Dynamics ──────▶ Mechanics
                (먼저 느낀다)        (행동을 알아챈다)    (규칙은 나중에 안다)
```

개발자는 메커닉만 직접 바꿀 수 있지만, 플레이어가 평가하는 것은 미학입니다. 그래서 설계는 **원하는 미학을 먼저 정하고 → 그 감정을 만드는 다이내믹을 상상하고 → 그 다이내믹이 생기게 하는 메커닉을 고르는** 역방향으로 합니다. React 비유를 들자면, 사용자는 컴포넌트 구조가 아니라 "빠르고 편하다"는 느낌으로 앱을 평가하는 것과 같습니다.

MDA 논문은 미학을 8가지로 분류합니다. 모든 게임이 전부를 가질 필요는 없고, **2~3개를 주력으로 고르는 것**이 요점입니다.

| 미학 | 설명 | 서바이버라이크에서 |
|---|---|---|
| Sensation (감각) | 감각적 쾌감 | ★ 화면 가득 터지는 적, 코인 흡수 소리 (16장) |
| Fantasy (판타지) | 다른 존재가 되는 경험 | ★ 약자 → 학살자로 변하는 파워 판타지 |
| Narrative (서사) | 이야기 전개 | 약함 |
| Challenge (도전) | 장애물 극복 | ★ 버티기, 보스 |
| Fellowship (교류) | 사회적 경험 | 약함 (공략 공유 정도) |
| Discovery (발견) | 미지의 탐험 | 무기 조합·진화 발견 |
| Expression (표현) | 자기 표현 | ★ 나만의 빌드 |
| Submission (몰입적 소일거리) | 머리 비우고 즐기는 시간 | ★ 한 판 더, 멍하게 이동하며 쌓이는 성장 |

### 코어 루프와 메타 루프

**코어 루프**는 플레이어가 수십 초 단위로 반복하는 행동의 순환입니다. **메타 루프**는 여러 판(세션)에 걸친 성장의 순환입니다. 좋은 루프는 각 단계의 출력이 다음 단계의 입력이 됩니다.

```
                  ┌──────────── 코어 루프 (약 20~40초) ────────────┐
                  │                                                │
                  ▼                                                │
         ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
         │ 이동하며 생존   │──▶│ 자동 공격으로   │──▶│ 코인 수집       │
         │ (위협 회피)     │    │ 적 처치         │    │ (위험 지역 진입) │
         └────────────────┘    └────────────────┘    └────────────────┘
                  ▲                                          │
                  │         ┌────────────────┐               │
                  └─────────│ 레벨업 3택1     │◀──────────────┘
                            │ (더 강해짐)     │
                            └────────────────┘

                  ┌──────────── 메타 루프 (판 1회 = 약 10분) ──────────┐
                  ▼                                                   │
         ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
         │ 한 판 플레이    │──▶│ 남은 코인 정산  │──▶│ 영구 강화·해금   │
         └────────────────┘    └────────────────┘    └────────────────┘
```

루프를 그렸다면 **각 화살표에 "왜 다음 단계로 가고 싶은가"를 적어 보세요.** 답이 없는 화살표가 약한 고리입니다.

| 화살표 | 동기 | 약하면 생기는 증상 |
|---|---|---|
| 생존 → 처치 | 적이 막고 있어서 치워야 함 | 도망만 다녀도 됨 → 지루 |
| 처치 → 수집 | 코인이 떨어진 곳이 위험해서 결정이 필요 | 코인이 자동으로 빨려옴 → 수집이 의미 없음 |
| 수집 → 레벨업 | 강해져야 다음 위협을 버팀 | 레벨업해도 체감 없음 |
| 레벨업 → 생존 | 새 능력을 써보고 싶음 | 선택지가 뻔함 |
| 판 종료 → 강화 | 다음 판을 더 멀리 가고 싶음 | 영구 강화가 너무 비싸거나 너무 쌈 |

이 장 첫머리의 "뭘 하면 되는 거야?"는 **처치 → 수집** 화살표와 **메타 루프 전체**가 비어 있어서 생긴 증상입니다.

### 서바이버라이크 장르 해부: 왜 재밌는가

서바이버라이크(뱀파이어 서바이버즈류)는 조작이 이동뿐인데도 많은 사람을 붙잡았습니다. 그 이유를 MDA로 분해하면 설계에 쓸 수 있는 부품이 됩니다.

| 재미 요소 | 메커닉 | 다이내믹 | 미학 |
|---|---|---|---|
| **파워 판타지** | 적 수는 선형 이상으로 늘지만 플레이어 화력은 레벨업마다 곱으로 증가 | 처음엔 도망치다 후반엔 적 무리 속으로 돌진 | Fantasy, Sensation |
| **빌드 조합** | 무기·패시브 조합에 시너지, 특정 조합의 진화 | 매 판 다른 목표 빌드를 노림, 선택지를 저울질 | Expression, Discovery |
| **짧은 세션** | 한 판이 정해진 시간에 끝남, 판 종료 시 보상 | "한 판만 더" 반복 | Submission |
| **선택의 긴장** | 3택1, 코인이 위험 지역에 떨어짐 | 위험을 감수할지 계산 | Challenge |
| **낮은 진입 장벽** | 이동만 입력, 공격 자동 | 누구나 첫 판에 2~3분 생존 | Submission |

이 표에서 장르의 공식이 보입니다. **조작을 줄인 대신 "결정"에 집중시킨다**는 것입니다. 그러므로 코인 러시가 강화해야 할 곳도 조작이 아니라 결정입니다.

### 훅(Hook) 한 문장

훅은 "이 게임을 왜 해야 하는가"를 한 문장으로 말한 것입니다. 스토어 페이지, 트레일러 첫 3초, 지인에게 설명할 때 모두 이 문장이 뼈대가 됩니다(27장에서 마케팅용으로 다시 다룹니다). 개발 단계에서는 **결정 필터** 역할이 더 중요합니다. 새 기능이 훅을 강화하지 않으면 뒤로 미룹니다.

좋은 훅의 공식은 대략 이렇습니다.

```
[익숙한 장르/경험] + [한 가지 비틀기] + [그 비틀기가 만드는 감정/결정]
```

| 나쁜 훅 | 무엇이 문제인가 |
|---|---|
| "재밌고 중독성 있는 서바이버라이크" | 형용사뿐, 차별점 없음 |
| "100종의 무기와 50종의 적" | 규모 자랑 — 1인 개발로 이길 수 없는 싸움 |
| "코인을 모으는 게임" | 비틀기가 없음 |
| **"코인이 곧 경험치이자 화폐인 서바이버라이크 — 판 안 제단에 써서 살아남을 것인가, 모아서 판 밖 영구 강화로 강해질 것인가"** | 장르 + 비틀기 + 결정이 모두 있음 |

### 레퍼런스 해부 방법

같은 장르의 잘 된 게임을 "즐기는" 것과 "해부하는" 것은 다릅니다. 해부할 때는 기록합니다. 다음 템플릿을 게임마다 한 장씩 채웁니다.

```
[플레이 기록 템플릿]
게임명 / 버전 / 플랫폼 / 플레이 시간(누적) / 기록 날짜

1. 첫 5분 타임라인 (분:초 단위로 무슨 일이 있었고 무엇을 느꼈나)
2. 코어 루프 다이어그램 (직접 그림)
3. 메타 루프: 판 사이에 무엇이 남는가, 얼마나 자주 새 것이 열리는가
4. 결정 목록: 한 판에서 내린 "고민되는" 결정 3개
5. 좌절 순간: 짜증났던 순간과 그 원인 (내 실수? 불공정?)
6. "한 판 더"를 누른 이유 / 끈 이유
7. 수치 메모: 판 길이, 레벨업 횟수, 첫 보스 시각
8. Steam 부정 리뷰 상위 10개의 공통 불만 (장르 유저가 원하는 것이 적혀 있음)
9. 훔칠 것 1개 / 피할 것 1개
```

세 가지 규칙을 지킵니다.

1. **첫 판은 공략을 보지 않고** 기록합니다. 신규 유저의 경험은 한 번뿐입니다.
2. **느낌이 아니라 사건을** 적습니다. "지루했다"가 아니라 "4분부터 7분까지 새 적이 없었다".
3. **부정 리뷰**를 반드시 읽습니다. 긍정 리뷰는 장르의 장점을, 부정 리뷰는 장르의 빈틈을 알려줍니다.

### 1페이지 기획서 vs 긴 GDD

GDD(Game Design Document)는 게임의 설계를 담은 문서입니다. 대형 스튜디오의 수백 쪽짜리 GDD는 여러 팀이 같은 그림을 보기 위해 필요하지만, 1인 개발에서는 **쓰는 순간부터 낡기 시작하는 문서**가 됩니다.

| | 1페이지 기획서 | 긴 GDD |
|---|---|---|
| 목적 | 방향 고정, 스코프 제한, 결정 필터 | 세부 명세 공유 |
| 분량 | A4 1장 (화면 한 번 스크롤) | 수십~수백 쪽 |
| 갱신 | 큰 방향이 바뀔 때만 | 계속 (현실적으로 안 됨) |
| 1인 개발 적합성 | 높음 | 낮음 — 세부는 코드·SO 에셋·스프레드시트가 진실의 원천 |

1인 개발자의 추천 구성은 **1페이지 기획서 + 살아있는 부속 문서**입니다. 수치는 스프레드시트(23장), 웨이브는 WaveData 에셋(22장), 이벤트 사양은 표(24장)가 담당합니다. 웹 개발로 치면 README(1페이지)와 타입 정의·테스트(살아있는 명세)의 관계입니다.

1페이지 기획서의 필수 항목은 다음과 같습니다.

```
1. 제목 / 훅 한 문장
2. 장르·플랫폼·타깃 플레이어·세션 길이
3. 디자인 기둥(Pillars) 3개 — 모든 결정의 기준
4. 코어 루프 / 메타 루프
5. 차별점 — 레퍼런스 대비
6. 콘텐츠 스코프 (숫자로)
7. 수익 모델
8. 일정 마일스톤
9. 가장 큰 위험 3개와 검증 방법
```

### 기능 우선순위: MoSCoW

MoSCoW는 기능을 네 칸으로 나누는 방법입니다.

| 분류 | 뜻 | 판단 질문 |
|---|---|---|
| **M**ust have | 없으면 게임이 성립하지 않음 | "이게 없어도 훅이 전달되는가?" → 아니오 |
| **S**hould have | 중요하지만 없어도 출시는 가능 | 출시 품질을 크게 올림 |
| **C**ould have | 있으면 좋음 | 여유가 생기면 |
| **W**on't have (this time) | 이번 버전엔 안 함 | 명시적으로 적어서 미련을 끊음 |

1인 개발에서 가장 중요한 칸은 **Won't**입니다. 적어두지 않은 아이디어는 개발 도중 계속 돌아와 스코프를 부풀립니다(29장에서 스코프 관리를 더 다룹니다). 경험칙으로 Must는 전체의 절반을 넘지 않게 합니다.

### 그레이박스 프로토타입 원칙

그레이박스는 회색 사각형과 원만으로 게임을 만들어 **재미를 먼저 검증**하는 방법입니다. 원칙은 다섯 가지입니다.

1. **질문 하나를 정한다.** "재밌는가?"는 질문이 아닙니다. "플레이어가 코인을 쓸지 모을지 고민하는가?"처럼 관찰 가능한 질문이어야 합니다.
2. **아트·사운드·UI 장식 금지.** 예쁘면 재미없는 루프를 가립니다. 반대로 사각형으로도 재밌으면 아트는 그것을 증폭할 뿐입니다.
3. **기한을 정한다.** 1~2주. 넘기면 질문이 너무 크다는 신호입니다.
4. **버릴 코드라고 선언한다.** 프로토타입 코드는 빠르게, 지저분하게. 검증되면 1부의 구조로 다시 씁니다. (JS: 해커톤 코드를 프로덕션에 그대로 올리지 않는 것과 같습니다.)
5. **성공·실패 기준을 미리 적는다.** 결과를 본 뒤 기준을 정하면 무엇이든 성공처럼 보입니다.

다행히 코인 러시는 1~2부에서 이미 뼈대가 있습니다. 새 메커닉(아래 실습의 "코인 제단")만 기존 프로젝트의 별도 씬에서 사각형으로 붙여 보면 됩니다.

### 2단계: 차별점 도출

해부표를 보면 차별점을 정할 때 흔히 하는 착각이 드러납니다. 처음 떠올린 아이디어는 "코인이 경험치이자 재화"였습니다. 그런데 표를 채워보니 **Brotato가 이미 한 재화로 성장과 상점 구매를 겸합니다.** 해부를 하지 않았다면 이미 있는 것을 차별점이라고 믿고 개발했을 것입니다.

그래서 한 칸을 더 파고듭니다. 세 게임의 "재화가 어디로 흘러가는가"를 비교합니다.

```
Vampire Survivors:  경험치 ─▶ 판 안에서 소멸          골드 ─▶ 메타(영구 강화)
                    (두 흐름이 분리됨 — 긴장 없음)

Brotato:            재료 ─▶ 경험치 + 판 안 상점
                    (판 안에서 성장 vs 구매의 긴장. 판 밖으로 가져가는 영구 스탯은 약함)

코인 러시(목표):    코인 ─┬▶ 경험치 (주우면 자동, 소모되지 않음)
                         ├▶ 판 안 제단에서 소비 (즉시 강화, 생존율↑)
                         └▶ 판 끝에 남은 만큼 영구 강화로 이월 (다음 판↑)
                    (긴장: "지금 살아남기" vs "장기적으로 강해지기")
```

차별점은 "한 재화가 경험치이자 화폐"가 아니라 **"판 안 소비와 판 밖 저축이 같은 코인을 두고 경쟁한다"** 로 좁혀졌습니다. 이것을 만드는 메커닉을 정의합니다.

| 메커닉 | 규칙 (초안) | 의도한 다이내믹 |
|---|---|---|
| 코인 = 경험치 | 코인을 주우면 경험치 바에 같은 양이 들어감. 경험치는 소모되지 않음 | 줍는 행위가 항상 이득 → 위험 지역으로 들어갈 동기 |
| 코인 지갑 | 주운 코인은 지갑에도 쌓임 | 판 종료 시 남은 지갑 = 메타 재화 |
| 코인 제단 | 2분마다 맵에 제단 등장, 30초간 유지. 코인을 내고 강력한 강화 1개 구매. 가격은 등장할 때마다 상승 | "지금 사서 이번 판 클리어" vs "모아서 영구 강화" |
| 사망·중도 종료 시 정산 | 사망하거나 판 도중 종료해도 지갑 코인은 100% 이월 (클리어 시 보너스 +50%). 판 자체는 재개하지 않음 | 저축 전략을 지나치게 벌하지 않되, 클리어 동기는 유지. 기둥 2 "언제 끊어도 손해 보지 않는다" |

마지막 행의 "사망해도 100% 이월"은 설계 결정입니다. 이월 비율을 낮추면 긴장이 커지지만 초보자의 좌절도 커집니다. 이런 결정은 기획서에서 확정하지 않고 **플레이테스트 질문**으로 넘깁니다(24장).

### 4단계: MoSCoW 기능 표

`Docs/features.md`의 완성 예시입니다. 각 기능에 **어떤 기둥을 위한 것인지**를 붙이면 논쟁이 짧아집니다.

| 기능 | 분류 | 기둥 | 근거 |
|---|---|---|---|
| 이동·자동 공격·적 추적 | Must | 2 | 장르 성립 조건 |

| 캐릭터 3종 | Should | 1 | 반복 플레이 동기 |

Must가 17개 중 7개입니다. 절반을 넘지 않습니다. 세이브를 Must로 둔 이유에 주목하세요. "저축"이 훅의 절반인데 저장이 없으면 저축이 존재하지 않고, 기둥 2의 "언제 끊어도 손해 보지 않는다"도 지킬 수 없습니다. 그래서 기획서에 **손실 범위**까지 적습니다: 판 도중 종료하면 그 판은 재개하지 않지만 그때까지의 지갑 코인은 사망과 같게 100% 이월하고, 재화가 바뀌는 순간(판 정산, 영구 강화 구매)마다 즉시 저장합니다.

```
  - 제단 위에서 상호작용 키 → 강화 3개 중 1 구매 (텍스트 버튼만) 또는 "모으기"로 닫기
  - 가격 100 → 200 → 300 → 400
  - 판 끝: 남은 코인을 PlayerPrefs에 누적 저장, "영구 공격력 +10% 구매 (N코인)" 버튼 하나
  - 영구 강화는 이 한 종류만, 그러나 **실제로 다음 판 공격력에 적용**한다
    (저축의 효용을 체감하지 못하면 "모을까"는 문구 이해 테스트가 된다)

만들지 않는 것
  아트, 사운드, 애니메이션, 영구 강화 2·3번째 종류, 제단 연출, 밸런스 조정

진행
  - 참가자 1명당 **3판 연속** (한 판 약 10분 + 판 사이 강화 화면). 같은 사람이
    판이 거듭되며 선택을 바꾸는지가 관찰 대상이다
  - 각 판 시작 전에 저장 코인·영구 강화 레벨을 확인해 기록 (초기화 실수 방지)

측정 (24장의 로컬 로그를 미리 쓰거나 손으로 기록)
  제단 방문마다 한 줄:
    참가자 / 판 번호 / 시각 / 체력 % / 지갑 / 가격 / 살 수 있었나(지갑 ≥ 가격) / 선택 / 머문 시간
  판이 끝날 때마다 한 줄: 이월 코인 / 영구 강화 구매 여부
  플레이 후 질문: 방문 기록을 함께 보며 "여기서는 왜 샀나요 / 왜 모았나요?"

성공 기준 (테스트 전에 확정) — 분모는 "살 수 있었던 방문"만
  - 5명 중 4명 이상이 살 수 있었던 방문에서 구매와 모으기를 **각각 한 번 이상** 선택
    (전체 구매율 40%라도 2명은 항상 사고 3명은 항상 안 사면 실패로 본다)
  - 선택이 바뀐 참가자 중 3명 이상이 그 이유를 체력·지갑·다음 판 목표 같은
    **상황 차이**로 설명 ("이번엔 체력이 없어서", "다음 판에 강화 사려고")
  - 보조 지표: 살 수 있었던 방문의 전체 구매율 20~80%
    (머문 시간은 고민의 증거가 아니라 설명을 못 읽은 결과일 수도 있어 기준에 쓰지 않는다)

실패 시 다음 수
  - 대부분 항상 산다 → 이월 가치(영구 강화 효과)를 키우거나 제단 효과를 약화
  - 대부분 항상 안 산다 → 제단 효과가 체감되지 않음, 강화 폭 확대 또는 가격 인하
  - 살 수 있었던 방문 자체가 적다 → 가격이 코인 공급보다 비쌈 (22장에서 계산)
  - 이유가 "뭔지 몰라서" → 가격·효과·이월 가치 표시 문제 (UI부터 확인)

일정
  1~3일  제단 오브젝트·구매·가격 상승
  4~5일  판 끝 저장·영구 공격력 1종 실제 적용, 방문 로그
  6~7일  자기 테스트 10판, 버그 수정
  8~10일 5인 × 3판 테스트 (24장 방식)
  11일   결론 문서: 유지 / 수정 / 폐기
```

### 확인하기

다음이 모두 "예"이면 이 장의 실습은 성공입니다.

- `Docs/` 에 `references.md`, `one-pager.md`, `features.md`, `prototype-plan.md` 네 파일이 있다.
- 1페이지 기획서를 처음 보는 사람에게 30초 보여주고 "이 게임에서 뭘 고민하게 돼?"라고 물었을 때 제단/저축 이야기가 나온다.
- 해부표의 "훔칠 것/피할 것" 각 항목이 MoSCoW 표나 기둥 어딘가에 반영되어 있다.
- 그레이박스 계획의 성공 기준이 숫자나 관찰 가능한 행동으로 적혀 있고, 분모(살 수 있었던 방문)와 참가자별 판정이 명시되어 있다.

## 흔한 실수

1. **증상**: 기획서가 30쪽이 되었고 한 달째 코드를 못 짰다. → **원인**: GDD를 명세서처럼 쓰려 함. → **해결**: 1페이지로 줄이고, 세부는 SO 에셋·스프레드시트·코드에 맡깁니다. 1페이지에 안 들어가면 스코프가 큰 것입니다.
2. **증상**: 차별점이 "더 예쁜 그래픽", "더 많은 무기"다. → **원인**: 규모로 경쟁하려 함. → **해결**: 레퍼런스 해부표에서 "재화가 어디로 흐르는가", "결정이 어디서 생기는가" 같은 구조 비교 행을 추가해 구조적 비틀기를 찾습니다.
3. **증상**: 그레이박스를 만들다 보니 캐릭터 애니메이션과 파티클까지 붙이고 있다. → **원인**: 질문이 정해지지 않아 "좋아 보이게" 만드는 쪽으로 흐름. → **해결**: 계획서의 "만들지 않는 것" 목록을 모니터 옆에 붙입니다. 기한이 지나면 무조건 테스트합니다.
4. **증상**: 테스트 후 "그래도 괜찮았던 것 같다"며 모든 기능을 유지한다. → **원인**: 성공 기준을 사후에 정함. → **해결**: 계획서의 성공 기준을 테스트 전에 커밋해 두고, 기준 미달이면 수정/폐기 중 하나를 반드시 고릅니다.
5. **증상**: 레퍼런스를 50시간 했지만 기록이 없다. → **원인**: 즐기기와 해부를 구분하지 않음. → **해결**: 해부 세션은 타이머를 켜고 템플릿을 옆에 띄운 채로만 합니다. 첫 판 기록은 다시 얻을 수 없으니 특히 먼저 적습니다.
6. **증상**: 기둥이 "재밌다, 쉽다, 예쁘다"라서 어떤 결정에도 도움이 안 된다. → **원인**: 누구나 동의하는 문장. → **해결**: "이 기둥 때문에 포기하는 것"이 떠오르지 않으면 기둥이 아닙니다. 기둥에 우선순위를 매깁니다.

## 연습 문제

**1. ★☆☆ MDA 분류하기**
다음 요소를 M/D/A 중 하나로 분류하세요: (a) 적이 플레이어 방향으로 초속 1.5로 이동한다, (b) 플레이어가 적 무리를 원형으로 끌고 다닌다, (c) "살았다!" 하는 안도감, (d) 레벨업 선택지는 3개다, (e) 코인 더미를 보고 일부러 위험 지역에 뛰어든다.

<details><summary>힌트·해설</summary>

(a) M — 수치로 정의된 규칙. (b) D — 누구도 "원형으로 끌고 다녀라"라고 코딩하지 않았지만 추적 AI와 이동만 입력이라는 메커닉에서 생긴 행동. (c) A — 감정. (d) M. (e) D — "코인이 위험 지역에 떨어진다"는 메커닉과 "코인이 경험치다"라는 메커닉이 만나 생긴 행동 패턴이며, 이 다이내믹이 Challenge 미학을 만듭니다. 설계자가 (e)를 원한다면 코인이 적 사망 위치에 떨어지게 하고, 자석 범위를 초반에 작게 두는 메커닉을 고릅니다.

</details>

**2. ★★☆ 약한 고리 찾기**
코어 루프에서 "처치 → 수집" 화살표가 약한 설계를 두 가지 떠올리고, 각각 메커닉 하나를 바꿔 고치세요.

<details><summary>힌트·해설</summary>

예시 1: 코인이 화면 어디서든 자동으로 빨려온다 → 수집에 결정이 없음. 해결: 기본 자석 범위를 작게, 자석 강화는 레벨업·영구 강화 선택지로. 예시 2: 코인이 몇 초 뒤 사라지지 않는다 → 적이 다 정리된 뒤 여유롭게 주우면 됨. 해결: 코인이 일정 시간(예: 15초) 후 사라지거나, 반대로 한 곳에 모여 "코인 더미"가 되어 위험하지만 큰 보상이 되게. 어느 쪽이든 기둥 1(30초마다 결정)을 강화하는지로 판단합니다.

</details>

**3. ★★☆ 훅 고쳐 쓰기**
다음 훅을 "익숙한 장르 + 비틀기 + 결정/감정" 공식으로 고쳐 쓰세요: "귀여운 캐릭터와 다양한 무기로 몬스터를 물리치는 중독성 있는 액션 게임".

<details><summary>힌트·해설</summary>

원문은 형용사(귀여운, 다양한, 중독성 있는)뿐이고 비틀기가 없습니다. 비틀기를 하나 정해야 고칠 수 있습니다. 예: "무기가 10초마다 무작위로 바뀌는 서바이버라이크 — 손에 쥔 것으로 어떻게든 버텨라". 또는 "적을 쓰러뜨리면 그 적이 내 무기가 되는 액션 로그라이트 — 어떤 적을 남겨둘 것인가". 좋은 훅은 읽는 순간 게임 장면 하나와 고민 하나가 떠오릅니다.

</details>

**4. ★★★ 내 게임의 문서 세트 만들기**
자기 게임 아이디어(코인 러시를 변형해도 됩니다)로 이 장의 네 문서를 모두 작성하세요. 레퍼런스는 3개, 각 3판 이상. 완성 후 개발자가 아닌 지인에게 1페이지 기획서만 보여주고 "이 게임에서 무엇을 고민하게 될 것 같은지" 물어 답을 기록하세요.

<details><summary>힌트·해설</summary>

점검 순서: (1) 해부표에 구조 비교 행("재화 흐름", "결정 지점")이 있는가. (2) 차별점이 해부표의 빈칸에서 나왔는가 — 이미 있는 것을 차별점이라 믿고 있지 않은가. (3) 기둥에 우선순위가 있는가. (4) MoSCoW의 Must가 절반 이하이고 Won't가 3개 이상인가. (5) 그레이박스 성공 기준이 숫자나 관찰 가능한 행동인가. 지인의 답이 여러분이 의도한 결정과 다르면 기획서가 아니라 훅 문장부터 다시 씁니다.

</details>

## 셀프 체크

**1. MDA에서 설계자가 "역방향"으로 생각해야 하는 이유를 설명해보세요.**

<details><summary>모범 답안</summary>

개발자가 직접 바꿀 수 있는 것은 메커닉뿐이지만, 플레이어는 미학(느낌)으로 게임을 경험하고 평가합니다. 메커닉에서 출발해 기능을 쌓으면 어떤 감정이 생길지 우연에 맡기게 됩니다. 그래서 원하는 미학을 먼저 정하고, 그 감정을 만드는 다이내믹을 상상한 뒤, 그 다이내믹이 생기게 하는 메커닉을 고릅니다. 다이내믹은 직접 만들 수 없고 메커닉과 입력의 상호작용으로만 생기므로 반드시 플레이로 확인해야 합니다.

</details>

**2. 코어 루프 다이어그램에서 "약한 고리"를 찾는 방법은 무엇인가요?**

<details><summary>모범 답안</summary>

각 화살표에 "플레이어가 왜 다음 단계로 가고 싶은가"를 적습니다. 동기를 적을 수 없거나 "그냥 자동으로 된다"라고 적히는 화살표가 약한 고리입니다. 예를 들어 코인이 자동으로 빨려오면 처치 → 수집 사이에 동기도 결정도 없습니다.

</details>

**3. 코인 러시의 차별점이 "코인이 경험치이자 화폐"에서 "판 안 소비와 판 밖 저축의 경쟁"으로 좁혀진 과정을 설명해보세요.**

<details><summary>모범 답안</summary>

레퍼런스 해부표를 채우다가 Brotato가 이미 한 재화로 경험치와 판 안 상점 구매를 겸한다는 것을 발견했습니다. 그래서 "재화가 어디로 흘러가는가"를 비교하는 행을 추가했고, VS는 경험치와 메타 재화가 분리되어 있고 Brotato는 판 안 소비가 중심이라는 차이를 확인했습니다. 코인 러시는 같은 코인이 판 안 즉시 강화와 판 밖 영구 강화 사이에서 경쟁하게 만들어, 두 레퍼런스가 비워둔 "지금 vs 나중" 결정을 차별점으로 삼았습니다.

</details>

**4. 1인 개발에서 긴 GDD 대신 1페이지 기획서를 권하는 이유는?**

<details><summary>모범 답안</summary>

긴 GDD는 여러 사람이 같은 명세를 봐야 할 때 가치가 있지만, 1인 개발에서는 갱신 비용이 커서 금방 코드와 어긋나 낡은 문서가 됩니다. 1페이지 기획서는 방향·기둥·스코프만 고정해 결정 필터로 쓰고, 세부 명세는 SO 에셋·스프레드시트·코드처럼 실제로 실행되는 "살아있는" 곳에 둡니다. 또 1페이지에 안 들어간다는 사실 자체가 스코프 초과 경고가 됩니다.

</details>

**5. MoSCoW에서 1인 개발자에게 Won't 칸이 특히 중요한 이유는?**

<details><summary>모범 답안</summary>

적어두지 않은 아이디어는 개발 중 계속 떠올라 "이것도 넣으면 좋겠다"로 스코프를 늘립니다. Won't에 이유와 함께 명시하면 이미 판단을 끝낸 문제라는 기록이 남아 반복되는 고민을 끊을 수 있습니다. 또 "이번 버전에는"이라는 단서 덕분에 아이디어를 버리는 부담 없이 미룰 수 있습니다.

</details>

**6. 그레이박스의 성공 기준을 테스트 전에 정해야 하는 이유는?**

<details><summary>모범 답안</summary>

결과를 본 뒤 기준을 정하면 확증 편향으로 어떤 결과든 "그럭저럭 성공"으로 해석하게 됩니다. 미리 "살 수 있었던 방문에서 5명 중 4명 이상이 구매와 모으기를 모두 한 번 이상 선택"처럼 관찰 가능한 기준과 분모를 정해두면 유지·수정·폐기 결정을 객관적으로 내릴 수 있고, 실패했을 때의 다음 수도 미리 준비할 수 있습니다. 기준을 미리 정하다 보면 "전체 구매율 40%"처럼 참가자별로는 고민이 없어도 통과하는 허술한 기준도 테스트 전에 걸러집니다.

</details>

## 핵심 요약

- 재미는 MDA로 분해합니다. 개발자는 메커닉만 만들 수 있고 플레이어는 미학으로 평가하므로, 설계는 미학 → 다이내믹 → 메커닉 역방향으로 합니다.
- 코어 루프(수십 초)와 메타 루프(판 단위)를 그리고, 각 화살표의 "다음으로 가고 싶은 이유"를 적어 약한 고리를 찾습니다.
- 서바이버라이크의 재미는 파워 판타지, 빌드 조합, 짧은 세션, 선택의 긴장이며, 조작을 줄인 대신 결정에 집중시키는 장르입니다.
- 훅은 "익숙한 장르 + 비틀기 + 결정/감정" 한 문장이며, 개발 중에는 기능을 거르는 필터입니다.
- 레퍼런스는 템플릿으로 기록하며 해부하고, 부정 리뷰에서 빈틈을 찾습니다. 해부는 "이미 있는 차별점"을 걸러줍니다.
- 1인 개발은 1페이지 기획서 + 살아있는 부속 문서(SO·스프레드시트·코드) 조합이 현실적입니다.
- MoSCoW에서 Must는 절반 이하, Won't는 반드시 채웁니다.
- 그레이박스는 질문 하나, 1~2주, 아트 금지, 사전 성공 기준으로 진행합니다. 검증하려는 결정에 필요한 효용(예: 저축의 실제 다음 판 효과)만큼은 가짜로 두지 않습니다.
