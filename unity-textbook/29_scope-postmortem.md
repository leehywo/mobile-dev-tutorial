# 29. 스코프·검증·포스트모템

> **이 장에서 배울 것**
> - 인디 게임이 끝나지 않는 구조적 원인(스코프 크립, 90-90 법칙, 완벽주의)을 설명할 수 있다
> - MoSCoW 기능 컷 표와 "출시 후 목록"으로 스코프를 고정한다
> - 킬 기준 문서(재미 판정, 위시리스트 목표, 날짜 기준)를 작성하고 그에 따라 계속·축소·중단을 결정할 수 있다
> - 3점 추정과 버퍼로 일정을 추정하고, 재정 런웨이를 계산한다
> - 번아웃 신호를 알아차리는 주간 루틴을 설계하고, 숫자가 들어간 포스트모템을 작성한다
>
> **선수 장**: 21, 24 · **예상 시간**: 3~4시간 · **코인 러시 진행**: 기능 컷 표, 킬 기준 문서, 런웨이 계산표, 출시 후 가상 포스트모템

## 왜 필요한가

코인 러시의 21장 기획서에는 "24주(약 6개월) 출시"라고 적혀 있습니다. 그런데 출시 예정이던 6개월째 개발 로그는 이렇습니다.

```
1개월  코어 루프 완성. 재미있다!
2개월  "캐릭터 3명은 너무 적어" → 8명으로. "무기 진화도 넣자"
3개월  "온라인 리더보드 있으면 좋겠다" → 서버 공부 시작
4개월  아트를 전부 픽셀에서 손그림으로 교체 결정
5개월  "보스 AI 가 단순해" → 행동 트리 직접 구현
6개월  기능은 70% 인데 버그 목록 140개. 출시일 미정. 매일 밤 "이번 주엔 끝내야지"
```

어느 결정도 그 순간에는 합리적이었습니다. 문제는 **결정의 기준이 없었다**는 것입니다. 무엇을 넣을지, 언제 멈출지, 언제 버릴지를 기분이 정했습니다.

웹 개발에서 스프린트 범위를 고정하고 "다음 릴리스로 미루기"를 하는 것처럼, 게임에도 범위 고정 장치가 필요합니다. 다만 게임은 "재미"라는 측정하기 어려운 요구사항이 있어서 더 쉽게 무너집니다. 이 장은 **끝내는 것을 시스템으로 만드는 문서들**을 코인 러시에 실제로 채워 봅니다.

## 개념

### 왜 인디 게임은 안 끝나는가

**① 스코프 크립(Scope Creep)** — 개발 중에 범위가 조금씩 늘어나는 현상입니다. 게임은 만들면서 아이디어가 계속 생기고, 혼자 개발하면 "안 된다"고 말해줄 PM 이 없습니다.

**② 90-90 법칙** — "코드의 처음 90%가 개발 시간의 90%를 쓰고, 나머지 10%가 또 다른 90%를 쓴다"는 농담입니다. 게임에서 마지막 10% 는 이런 것들입니다.

```
- 옵션 메뉴(해상도, 음량, 키 리바인딩, 언어)        - 세이브 마이그레이션, 엣지 케이스
- 모든 해상도·기기 대응, 게임패드 UI 포커스           - 튜토리얼, 첫 실행 경험
- 현지화 텍스트 넘침, 폰트 글리프 누락               - 크래시 리포트, 성능 최적화
- 스토어 에셋, 트레일러, 빌드 업로드, 플랫폼 인증      - 수백 개의 작은 버그
```

프로토타입에서는 이것들이 안 보이기 때문에, 1개월 만에 "거의 다 됐다"는 착각이 생깁니다.

**③ 완벽주의** — "이 정도로는 부끄러워서 못 낸다"는 감정입니다. 첫 게임은 누구에게나 부끄럽습니다. 출시하지 않은 게임은 피드백·매출·포트폴리오 어느 것도 만들지 못합니다.

**④ 검증 부재** — 재미와 시장성을 확인하지 않고 만들면, 방향이 틀렸을 때 수정 비용이 개발 기간에 비례해 커집니다.

### 게임잼으로 끝내는 근육 만들기

게임잼은 정해진 시간(보통 48~72시간, 행사에 따라 1~2주) 안에 주제에 맞는 게임을 만드는 행사입니다.

| 게임잼 | 특징 |
|---|---|
| GMTK Game Jam | 유튜브 Game Maker's Toolkit 주최. 참가자 규모가 크고 주제 해석이 중요 |
| Ludum Dare | 오래된 온라인 게임잼. 형식(개인/팀)과 규칙이 나뉨 |
| Global Game Jam | 전 세계 동시 개최, 현장(지역 사이트) 참가 가능. 국내 사이트도 운영됨 |

일정은 매년 itch.io/jams 와 각 공식 사이트에서 확인합니다.

게임잼이 훈련시키는 것:

- **스코프 감각**: "48시간에 이건 불가능"을 몸으로 배웁니다.
- **핵심만 남기기**: 메뉴·세이브·옵션 없이 코어 루프만으로 재미를 증명합니다.
- **제출 마감 경험**: 마감에 맞춰 빌드를 올리는 것 자체가 기술입니다.
- **즉각적 피드백**: 다른 참가자의 평가·댓글.

게임잼 규칙: 첫 6시간 안에 코어 루프가 돌아가야 하고, 마지막 6시간은 새 기능 금지(버그·빌드·페이지만).

### 출시 사다리

```
1단계  1개월 게임 × 2~3개      itch.io / 모바일           목표: "끝내기"와 빌드·업로드 경험
          │  (포스트모템)
2단계  3~6개월 게임 × 1~2개    Steam 또는 모바일 스토어    목표: 실제 판매, 스토어 페이지·마케팅 한 사이클
          │  (포스트모템 + 숫자)
3단계  6~12개월(전업 기준) 게임  위시리스트·지표로 검증된 기획만   목표: 수익
```

각 단계는 다음 단계의 **입장권**입니다. 1개월 게임을 끝내지 못했다면 3개월 게임은 끝나지 않습니다. 기간은 부업(주 15~20시간) 기준 달력 기간입니다. 이 교재의 일정 예시는 모두 2단계에 속하지만 용도가 다릅니다.

| 예시 | 범위 | 용도 |
|---|---|---|
| 21장·이 장의 코인 러시 **24주** 계획 | 21장 v1.0 스코프 전체 | 연재 게임의 개발·출시 계획. 이 장의 컷 표·킬 기준·포스트모템이 이 계획을 씁니다 |
| 26장 **D-180~D+30** 표 | Steam 행정·마케팅만 | 출시일에서 역산하는 표준 일정. 24주 계획에 겹칠 때의 조정은 26장 9단계에 있습니다 |
| 30장 **12주** 캡스톤 | 코인 러시 v1.0 보다 작은 자기 게임 | 2단계의 짧은 쪽. 첫 출시 경험이 목적이라 범위를 더 줄입니다 |

### 기능 컷 기준 — MoSCoW 와 "출시 후 목록"

**MoSCoW** 는 요구사항을 네 단계로 분류합니다.

| 분류 | 정의 | 판단 질문 |
|---|---|---|
| **Must** | 없으면 게임이 성립하지 않음 | 이게 없으면 코어 루프가 도는가? 플랫폼 필수 요건인가? |
| **Should** | 중요하지만 없어도 출시 가능 | 없으면 리뷰에 불만이 나올 것이 확실한가? |
| **Could** | 있으면 좋음 | 시간이 남으면? |
| **Won't (this time)** | 이번 출시에는 하지 않음 | → **출시 후 목록**으로 |

기능 하나를 평가할 때 쓰는 세 가지 축:

```
가치  : 코어 루프(21장)를 강화하는가? 훅(27장)에 기여하는가?
비용  : 3점 추정 기대값(일). 연쇄 작업(UI, 세이브, 밸런스, 현지화)까지 포함했는가?
위험  : 처음 해보는 기술인가? 다른 시스템을 흔드는가?
```

**출시 후 목록**은 아이디어를 버리는 곳이 아니라 **보관하는 곳**입니다. "나중에 한다"고 적어두면 지금 안 해도 불안하지 않습니다. 출시 후 리뷰에서 실제로 요청되는 항목만 꺼내면 됩니다.

범위 고정 규칙: **새 기능을 Must/Should 에 넣으려면 같은 비용의 기능을 빼야 합니다.** 스프린트에 티켓을 추가하면 다른 티켓을 빼는 것과 같습니다.

### 킬 기준 문서

킬 기준은 **감정이 개입하기 전에** 미리 정해두는 "계속/축소/중단" 조건입니다. 매몰 비용이 쌓인 뒤에는 누구나 "조금만 더"를 선택하기 때문입니다.

| 기준 유형 | 예 | 측정 방법 |
|---|---|---|
| **재미 판정** | 프로토타입 2주 후, 테스터 5명 중 3명 이상이 "한 판 더"를 자발적으로 요청 | 24장 플레이테스트 관찰 |
| **시장 검증** | Coming Soon 공개 N주 후 위시리스트 목표치 | Steamworks 리포트 |
| **날짜 기준** | 예정일 + 버퍼를 넘기면 자동으로 스코프 축소 회의 | 캘린더 |
| **재정 기준** | 런웨이가 N개월 이하로 떨어지면 부업 복귀 | 런웨이 표 |

결정은 세 가지 중 하나입니다.

```
계속(Go)    : 기준 충족. 다음 게이트까지 진행
축소(Pivot) : 일부 미달. 기능 컷·기간 단축 후 재평가 날짜 지정
중단(Kill)  : 핵심 기준 미달. 프로젝트 보관, 재사용 자산 추출, 포스트모템 작성
```

중단은 실패가 아니라 **남은 시간을 더 가능성 있는 프로젝트에 쓰는 결정**입니다. 중단한 프로젝트의 코드·툴·아트는 다음 게임의 자산이 됩니다.

### 일정 추정 — 3점 추정과 버퍼

개발자는 거의 항상 낙관적으로 추정합니다. **3점 추정(PERT)** 은 세 가지 값을 받아 기대값을 계산합니다.

```
O = 낙관(모든 게 순조로울 때)
M = 가장 가능성 높은 값
P = 비관(처음 해보는 일에서 막힐 때)

기대값 E = (O + 4M + P) / 6
표준편차 σ ≈ (P − O) / 6
```

예: Steam 업적 연동 — O=1일, M=2일, P=6일 → E = (1 + 8 + 6) / 6 = 2.5일, σ ≈ 0.83일.

작업 전체 합계에 **프로젝트 버퍼**를 더합니다. 계산 순서가 중요합니다.

```
① 가용 시간     = 기간(주) × 주당 시간
② 고정 업무 공제 = 마케팅(27장 주 3~4h) + 주간 계획·빌드 확인 + 플레이테스트 운영(24장)
                  + 출시 행정·스토어 페이지·빌드 검토 대응(26·28장)
③ 개발 가용     = ① − ②
④ 버퍼          = ③ × 20%   (첫 출시·처음 해보는 일이 많으면 25~30%)
⑤ 기능 예산     = ③ − ④     → Must+Should 기대값 합이 이 안에 들어가야 함
```

- **고정 업무를 먼저 빼야 합니다.** 기능 추정만 합산해 "가용 일수 안에 들어간다"고 판단하면, 마케팅·테스트·행정이 기능 시간을 잠식해 일정이 반드시 넘칩니다.
- "기대값 합에 25% 버퍼를 더한다"와 "개발 가용 시간의 80% 만 계획한다"는 **같은 규칙을 반대쪽에서 계산한 것**입니다(E × 1.25 = 가용 ⇔ E = 가용 × 0.8).
- 버퍼는 개별 작업의 추정값에 나눠 넣지 않고 **한 덩어리(프로젝트 버퍼)** 로 관리합니다. 작업마다 넣으면 파킨슨 법칙으로 다 써버립니다. 몇 달짜리 계획에서는 달력 끝에 모아 두고, 30장처럼 주 단위로 짧게 계획할 때는 매주 가용 시간의 20% 를 비워 두되 그 시간을 특정 작업에 배정하지 않고 **버퍼 잔고**로 누적합니다. 둘 다 "버퍼 잔고와 소진율을 주간 기록한다"는 점에서 같은 방식입니다.
- 부업 개발자는 "하루" 단위를 **실제 개발 가능 시간(예: 3시간)** 으로 환산합니다. 달력의 날과 개발 일을 혼동하면 일정이 두세 배 어긋납니다.

추정의 정확도는 기록으로 올라갑니다. 작업을 끝낼 때마다 추정값과 실제값을 적어 **자기 배수**(실제 ÷ 추정)를 알아두세요.

### 1인 개발 주간 루틴과 칸반

```
월  (1h) 주간 계획: 칸반 정리, 이번 주 목표 3개, 마케팅 녹화
화~목    개발 블록 (가장 어려운 작업을 에너지 높은 시간에)
금  (1h) 빌드 + 실기기 확인 + 이번 주 GIF 1개
토       개발 블록 또는 휴식 (격주)
일       완전 휴식 (컴퓨터 끄기)
매일 마지막 5분: "내일 처음 할 일" 한 줄 적기 → 다음 날 시작 마찰 제거
```

**칸반 보드** (Trello, GitHub Projects, Notion 등 아무거나):

| Backlog | This Week (최대 5) | Doing (최대 1~2) | Test | Done |
|---|---|---|---|---|
| Should/Could 기능 | 이번 주 목표 | 지금 하는 것 | 빌드에서 확인할 것 | 완료 |

- **Doing 칸 개수 제한**(WIP limit)이 핵심입니다. 1인 개발에서 동시에 3개를 열면 셋 다 안 끝납니다.
- 카드에는 MoSCoW 라벨과 추정값(E)을 적습니다.
- "Test" 칸은 에디터에서만 되는 기능이 Done 으로 가는 것을 막습니다([18장](./18_profiling-mobile.md) 실기기 테스트).

### 재정 런웨이 계산

```
런웨이(개월) = (현재 저축 + 확정된 수입) ÷ 월 순지출
월 순지출    = 월 생활비 + 월 개발비 − 월 확정 수입(부업 등)
```

- **출시 수익은 확정 수입에 넣지 않습니다.** 첫 게임 매출을 생활비 계획에 넣으면 출시 직후 판단이 흔들립니다.
- 비상금(보통 생활비 몇 개월 치)은 런웨이 계산에서 **제외**하고 따로 둡니다.
- 월 1회 실제 지출로 표를 갱신합니다.
- 전업 전환 판단은 런웨이 + "출시 경험 수" + "지표로 검증된 다음 기획" 세 가지를 함께 봅니다.

### 번아웃 신호와 대응

번아웃은 1인 개발자의 가장 흔한 중단 사유 중 하나입니다. 신호를 일찍 알아차리는 것이 중요합니다.

| 신호 | 예 | 대응 |
|---|---|---|
| 시작 회피 | 에디터 켜기가 두렵고 SNS·유튜브로 도피 | 작업을 15분짜리로 쪼개기, "내일 첫 할 일" 메모 |
| 감정 둔화 | 게임이 재미있는지 더는 모르겠음 | 1주 휴식 후 외부 테스터에게 판단 위임 (24장) |
| 신체 증상 | 수면 부족, 두통, 주말에도 피로 | 개발 시간 상한 설정, 운동, 필요시 전문가 상담 |
| 비교 불안 | 다른 개발자 성공 소식에 무기력 | SNS 사용 시간 제한, 생존자 편향 기억 |
| 끝없는 리팩터링 | 기능 대신 구조만 계속 고침 | 이번 주 목표를 "플레이어가 볼 수 있는 변화"로 제한 |

대응의 원칙: **휴식을 일정에 미리 넣고**, 동료(디스코드·오프라인 모임·글로벌게임센터 네트워크)를 만들며, 몸 상태가 심각하면 개발보다 건강을 우선하고 전문가의 도움을 받습니다.

### 포스트모템 형식

포스트모템은 프로젝트가 끝난 뒤(출시 또는 중단) 쓰는 회고 문서입니다. 인디 개발자에게 **다음 게임을 위한 가장 값진 자산**입니다.

```
1. 개요       : 게임 한 줄, 기간, 팀, 플랫폼, 가격, 도구
2. 숫자       : 계획 vs 실제 (기간, 비용, 위시리스트, 판매, 리뷰, 환불률, 플레이 시간)
3. 잘된 것    : 3~5개, 각각 "왜 잘됐는지"와 "다음에도 할 것"
4. 안 된 것   : 3~5개, 각각 "원인"과 "징후를 언제 봤어야 했는지"
5. 다음에 바꿀 것 : 구체적 행동 3개 (측정 가능한 문장)
6. 재사용 자산 : 코드·툴·아트·오디오·커뮤니티
```

좋은 포스트모템의 조건: **숫자가 있고**, 남 탓·운 탓이 아니라 **내가 통제할 수 있었던 것**에 집중하며, "다음에 바꿀 것"이 행동 문장입니다("마케팅 더 열심히" ✕ → "Coming Soon 을 개발 2개월 차에 연다" ○).

### 2단계 — 코드로 컷을 관리하기

잘라낸 기능 코드를 지우거나 긴 브랜치에 방치하면 나중에 되살리기 어렵습니다. 반쯤 만든 기능은 **플래그로 끄고 빌드에서 숨깁니다.**

`Assets/_CoinRush/Scripts/Core/FeatureCuts.cs`

```csharp
using UnityEngine;

/// <summary>
/// 이번 출시에서 끈 기능 스위치. 에셋 하나로 컷 현황을 한눈에 본다.
/// JS: 기능 플래그(feature flag) 설정 파일과 같은 역할.
/// </summary>
[CreateAssetMenu(fileName = "FeatureCuts", menuName = "CoinRush/Feature Cuts")]
public class FeatureCuts : ScriptableObject
{
    [Header("Could — 버퍼 잔고가 10일 이상일 때만 켠다")]
    [Tooltip("무기 진화 시스템 (E=5.5일)")]
    public bool weaponEvolution;

    [Header("Won't — 출시 후 목록")]
    [Tooltip("엔드리스 모드 (출시 후 1순위)")]
    public bool endlessMode;

    [Tooltip("두 번째 맵 (v1.1 후보)")]
    public bool secondMap;

    [Tooltip("온라인 리더보드")]
    public bool leaderboard;

    [Header("개발 빌드 전용")]
    [Tooltip("true 면 Development Build 에서만 위 기능을 강제로 켠다 (테스트용)")]
    public bool forceAllInDevelopmentBuild;

    public bool IsOn(bool flag)
    {
        if (forceAllInDevelopmentBuild && Debug.isDebugBuild) return true;
        return flag;
    }
}
```

사용 예 — 타이틀 메뉴에서 엔드리스 모드 버튼 숨기기:

`Assets/_CoinRush/Scripts/UI/TitleMenuCuts.cs`

```csharp
using UnityEngine;

public class TitleMenuCuts : MonoBehaviour
{
    [SerializeField] private FeatureCuts cuts;
    [SerializeField] private GameObject endlessModeButton;
    [SerializeField] private GameObject leaderboardButton;

    // 씬이 시작될 때 한 번만 읽는다. 출시 빌드에서 플래그는 바뀌지 않으므로 충분하다.
    private void Awake()
    {
        endlessModeButton.SetActive(cuts.IsOn(cuts.endlessMode));
        leaderboardButton.SetActive(cuts.IsOn(cuts.leaderboard));
    }
}
```

1. Project 창의 `Assets/_CoinRush/Data/` 에서 **Create → CoinRush → Feature Cuts** 로 에셋을 만들고 모든 값을 false 로 둡니다.
2. 타이틀 씬에 엔드리스 모드·리더보드 버튼이 없다면 임시 버튼 두 개(`EndlessButton`, `LeaderboardButton`)를 만듭니다.
3. 타이틀 씬의 메뉴 오브젝트에 `TitleMenuCuts` 를 붙이고 Inspector 에서 **Cuts** ← 1번의 FeatureCuts 에셋, **Endless Mode Button** ← `EndlessButton`, **Leaderboard Button** ← `LeaderboardButton` 을 드래그합니다.
4. 출시 빌드 전에 FeatureCuts 에셋을 열어 **Could/Won't 가 모두 꺼져 있는지** 확인하는 것을 26장 체크리스트 D-30 에 추가합니다.

> 이 코드는 `Awake` 에서 **한 번만** 값을 읽습니다. Play 중에 에셋의 체크박스를 바꿔도 버튼은 바뀌지 않으며, 그것이 의도한 동작입니다. 실행 중 토글이 필요하면 연습 문제 3처럼 변경 알림과 다시 적용하는 메서드를 따로 만듭니다.

### 3단계 — 킬 기준 문서 (완성본)

게이트 날짜는 21장 기획서의 마일스톤(2주 그레이박스, 8주 수직 슬라이스, 14주 Steam 페이지 공개, 24주 출시)에 맞춥니다. 모든 게이트는 **측정 결과가 어떤 값이 나와도 Go/Pivot/Kill 중 정확히 하나로 떨어지도록** 조건을 씁니다.

```
# 코인 러시 킬 기준 문서 v1.0
작성일: 개발 시작일 / 서명: (본인) / 검토자: 개발자 친구 1명 (결정 회의 동석)

## 원칙
- 이 문서는 개발 시작 전에 작성했고, 게이트 날짜 이전에는 기준을 바꾸지 않는다.
- 기준 변경은 게이트 회의에서 검토자와 함께, 변경 이유를 기록한 경우에만 한다.
- 결정은 계속(Go) / 축소(Pivot) / 중단(Kill) 중 하나로 반드시 내린다. "좀 더 보자"는 없다.
- 측정이 무효(표본 부족)이면 정해진 연장을 1회만 하고, 연장 뒤에도 무효면 "미달"로 본다.

## 게이트 1 — 재미 판정 (2주차 금요일, 재테스트 3주차 금요일)
대상: 21장 그레이박스 (이동, 적 3종, 무기 2종, 레벨업 3택1, 코인 제단, 5분 웨이브)
방법: 장르 경험자 5명 대면/화면공유 테스트 (24장 관찰 양식). 5명 미만이면 측정 무효.
지표: a = 제단 앞에서 3초 이상 멈춘 인원 (21장 성공 기준)
      b = 설명 없이 "한 판 더"를 요청한 인원
      c = 제단 구매율 (구매 ÷ 제단 방문)
Go    : a ≥ 4 AND b ≥ 3
Pivot : Go 가 아니고 (a ≥ 2 OR b ≥ 2)
        → 1주 동안 제단 가격·등장 주기·적 밀도 조정 후 **새 테스터 5명**으로 재테스트 1회
        → 재테스트에서 Go 조건 충족이면 Go, 아니면 Kill
Kill  : a ≤ 1 AND b ≤ 1 → 재테스트 없이 중단
보조  : Go 여도 c 가 10% 이하 또는 90% 이상이면 제단 수치 조정을 3주차 첫 작업으로 넣는다 (21장)

## 게이트 2 — 수직 슬라이스 + 시장 신호 (8주차 금요일)
대상: 아트·사운드·게임 필이 들어간 3분 구간
지표: v = 같은 채널(X)·같은 요일·시간대에 올린 짧은 영상 3개 중,
          "노출 대비 공유+저장 비율"이 그 채널 최근 게시물 10개 중앙값의 2배 이상인 영상 수
          (영상별 노출 500회 미만이면 그 영상은 측정 무효 → 1주 연장 재게시 1회)
      r = 테스터 5명 이상의 재플레이 의향 5점 척도 평균
Go    : v ≥ 1 AND r ≥ 3.5
Pivot : 둘 중 하나만 충족, 또는 둘 다 미달
        → 훅 문장·영상 장면 교체(27장) 후 10주차 금요일에 v·r 재측정
        → 재측정에서 Go 조건 충족이면 Go,
          아니면 Should 전부 컷 + 출시일 유지 (Kill 대신 "작게 출시 후 학습")
Kill  : 이 게이트에서는 없음 (출시 경험 자체가 목표이므로 축소 출시로 대신한다)

## 게이트 3 — 위시리스트 (Coming Soon 공개 14주차 → 측정 20주차 금요일)
목표치: 비교군 5개 게임의 출시 전 공개 기간·규모를 참고해 직접 정한 값 W (이 프로젝트는 W = 1,000 으로 가정)
측정: Steamworks 위시리스트 리포트의 누적 순 위시리스트
Go    : 누적 ≥ W → 예정대로 24주차 출시
Pivot : 0.5W ≤ 누적 < W → 출시일 유지, 추가 콘텐츠 개발 중단, 남은 기능 시간 절반을 마케팅(27장)에 배분
Kill(확장 중단) : 누적 < 0.5W → Could 전부 폐기, 현 상태로 최소 품질 확보 후 출시, 다음 프로젝트 기획 시작

## 게이트 4 — 날짜 (예정 출시일 = 시작 + 24주, 버퍼는 이미 24주 안에 포함)
매주 금요일 : 버퍼 잔고 기록. 잔고가 계획 소진선(주 0.75일)보다 5일 이상 빠르게 줄면 → Should 컷 회의
20주차 금요일 Must 미완료 → Should 전부 컷
24주차 출시 불가 → 출시 가능한 최소 범위로 2주 내 출시(빌드 검토 재제출 기간), 그 이후 연장 없음

## 게이트 5 — 재정
런웨이 표(아래)의 "남은 개월"이 6개월 이하로 떨어지면 → 외주·부업 수입 확보를 개발보다 우선

## 중단 시 할 일
1) 포스트모템 작성  2) 재사용 자산 목록화(코드·툴·에셋)  3) 커뮤니티에 정직하게 공지  4) 1주 휴식
```

### 4단계 — 런웨이 계산표

### 확인하기

- 기능 예산을 **가용 시간 − 고정 업무(마케팅·테스트·행정·주간 루틴) − 버퍼** 순서로 계산했고, Must+Should 합계가 그 안에 있습니다.

1단계 표처럼 ① 가용 시간 → ② 마케팅·테스트 운영·출시 행정·주간 루틴을 먼저 공제 → ③ 개발 가용 → ④ 버퍼 20~30% → ⑤ 기능 예산 순서로 계산하고, 시간을 개발일(예: 1일 = 3시간)로 환산합니다. 예산을 넘을 때 Should 를 먼저 Could 로 내리고, 그래도 넘으면 Must 의 **범위를 줄입니다**(무기 6종 → 3종, 21장이 허용한 최소치). Must 를 Won't 로 보내야 한다면 게임 컨셉 자체가 이 기간에 맞지 않는다는 신호이니 기획(21장)으로 돌아가세요.

</details>

**3. ★★☆** `FeatureCuts` 를 확장해 Development Build 에서만 보이는 "컷 현황 디버그 창"(OnGUI 또는 UGUI)을 만드세요. 각 플래그 이름과 on/off 를 표시하고 런타임에 토글할 수 있어야 합니다.

<details><summary>힌트·해설</summary>

`Debug.isDebugBuild` 가 false 면 컴포넌트를 비활성화합니다. 필드를 하나씩 하드코딩해도 되지만, 확장하려면 `System.Reflection` 으로 `FeatureCuts` 의 `bool` 공개 필드를 순회해 `GUILayout.Toggle` 로 그릴 수 있습니다. 런타임 토글은 ScriptableObject 에셋 값을 에디터에서 바꾸면 Play 종료 후에도 남는다는 점(03장)에 주의하세요 — 복제본(`Instantiate(cuts)`)을 만들어 조작하면 원본이 보존됩니다. 또 2단계의 `TitleMenuCuts` 는 `Awake` 에서만 값을 읽으므로 토글이 화면에 반영되지 않습니다. `FeatureCuts` 에 `public event System.Action Changed;` 와 `public void NotifyChanged() => Changed?.Invoke();` 를 두고, `TitleMenuCuts` 의 버튼 갱신을 `Refresh()` 메서드로 분리해 `OnEnable` 에서 `cuts.Changed += Refresh;`(해제는 `OnDisable`) 하면, 디버그 창에서 토글한 뒤 `NotifyChanged()` 를 호출할 때 즉시 갱신됩니다.

</details>

**4. ★★★** 자기 게임(진행 중이거나 중단한 것, 게임잼 결과물도 가능)의 포스트모템을 이 장의 6개 절 형식으로 작성하세요. 숫자 표는 최소 6개 지표, "안 된 것"에는 각각 "징후를 언제 봤어야 했나"를 포함하세요.

<details><summary>힌트·해설</summary>

숫자가 없다면 커밋 로그(`git log --since`), 캘린더, 영수증에서 기간·시간·비용을 복원하세요. 게임잼이라면 평가 점수·댓글 수·다운로드 수도 지표입니다. "안 된 것"은 결과("일정 초과")가 아니라 **원인**("추정에서 UI 포커스를 빠뜨림")을 적어야 다음 행동으로 이어집니다. 완성 후 다음 프로젝트의 킬 기준 문서에 반영할 줄을 최소 1개 찾으세요.

</details>

## 셀프 체크

**1.** 90-90 법칙이 인디 개발 일정에서 구체적으로 어떤 작업들로 나타나는지 설명해보세요.

<details><summary>모범 답안</summary>

프로토타입에서는 보이지 않는 옵션 메뉴, 해상도·기기 대응, 게임패드 UI 포커스, 세이브 엣지 케이스, 현지화 텍스트 문제, 튜토리얼, 스토어 에셋·빌드 업로드·플랫폼 요건, 다수의 작은 버그가 마지막 10% 에 몰려 초기 추정만큼의 시간을 추가로 씁니다. 그래서 이 묶음을 추정표에 별도 행으로 잡아야 합니다.

</details>

**2.** 킬 기준을 개발 시작 전에 정해야 하는 이유는?

<details><summary>모범 답안</summary>

개발이 진행될수록 매몰 비용과 애착이 커져 객관적 판단이 어려워지고, 결과를 본 뒤 기준을 결과에 맞춰 바꾸게 되기 때문입니다. 미리 정한 날짜·측정 방법·숫자 조건이 있어야 계속·축소·중단 결정을 감정이 아닌 기준으로 내릴 수 있습니다.

</details>

**3.** 3점 추정에서 기대값이 보통 가장 가능성 높은 값(M)보다 큰 이유와, 버퍼를 작업에 나누지 않고 한 덩어리로 관리하는 이유는?

<details><summary>모범 답안</summary>

개발 작업은 일찍 끝나는 폭보다 늦어지는 폭이 훨씬 커서 비관값 P 가 멀리 있으므로 (O + 4M + P)/6 이 M 보다 커집니다. 버퍼를 작업마다 나누면 각 작업이 주어진 시간을 다 쓰는 경향(파킨슨 법칙) 때문에 소진되므로, 한 덩어리(긴 계획은 달력 끝, 30장 같은 주 단위 계획은 매주 비워 둔 20% 의 누적 잔고)로 두고 실제로 늦어진 작업에만 쓰며 소진율을 관리합니다. "추정 합의 25% 를 버퍼로 더한다"와 "가용의 80% 만 계획한다"는 같은 규칙입니다.

</details>

**4.** 런웨이 계산에 첫 게임의 예상 매출을 넣으면 안 되는 이유는?

<details><summary>모범 답안</summary>

첫 게임 매출은 불확실성이 매우 크고 대부분 기대보다 낮기 때문에, 이를 넣으면 런웨이가 과대평가되어 전업 전환 같은 되돌리기 어려운 결정을 잘못 내리게 됩니다. 확정 수입만으로 계산하고 매출은 참고 열로 관리하며 실제 입금 후 반영합니다.

</details>

**5.** 좋은 포스트모템의 "다음에 바꿀 것"은 어떤 형태여야 하나요? 나쁜 예와 좋은 예를 들어보세요.

<details><summary>모범 답안</summary>

다음 프로젝트에서 실행 여부를 확인할 수 있는 구체적 행동 문장이어야 합니다. 나쁜 예는 "마케팅을 더 열심히 한다", 좋은 예는 "Coming Soon 페이지를 개발 2개월 차에 공개하고 주 3회 짧은 영상을 올린다"입니다.

</details>

## 핵심 요약

- 인디 게임이 안 끝나는 이유는 게으름이 아니라 **기준 없는 결정**(스코프 크립, 90-90, 완벽주의, 검증 부재)입니다.
- 게임잼과 출시 사다리(1개월 → 3~6개월 → 6~12개월)로 "끝내는 능력"을 단계적으로 증명합니다.
- 기능 예산은 가용 시간에서 고정 업무(마케팅·테스트·행정)와 버퍼를 먼저 뺀 값입니다. MoSCoW 표로 Must+Should 를 그 안에 넣고, 새 기능은 같은 비용을 빼야만 추가하며, 나머지는 출시 후 목록에 보관합니다.
- 킬 기준 문서는 개발 전에 날짜·측정 방법·숫자 조건으로 쓰고 게이트에서 Go/Pivot/Kill 을 반드시 결정합니다.
- 3점 추정 (O+4M+P)/6 과 한 덩어리로 관리하는 버퍼(추정 합의 25% 추가 = 가용의 80% 만 계획), 실제값 기록으로 자기 추정 배수를 압니다.
- 포스트모템의 판매량은 할인·지역 가격·환불·세금·수수료·송금을 뺀 **장당 순수입**과 손익분기 판매량으로 바꿔 읽습니다.
- 런웨이는 확정 수입만으로 계산하고, 비상금은 따로 둡니다.
- 주간 루틴·WIP 제한 칸반·휴식 일정으로 번아웃을 예방하고 신호가 보이면 작업을 쪼개거나 쉽니다.
- 포스트모템은 숫자, 원인과 징후, 측정 가능한 행동 3개, 재사용 자산으로 구성합니다.
