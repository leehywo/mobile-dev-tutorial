# 30. 캡스톤 — 3개월 출시 프로젝트

> **이 장에서 배울 것**
> - 1~29장의 내용을 12주 일정에 배치해 "자기 게임"의 출시 계획을 세울 수 있다
> - 2주차 재미 판정, 6주차 수직 슬라이스, 10주차 콘텐츠 동결 게이트를 기준에 따라 통과·판정한다
> - 기획서·웨이브/밸런스 표·테스트 리포트·스토어 페이지·출시 체크리스트·포스트모템 제출물을 템플릿대로 작성한다
> - 루브릭으로 자기 프로젝트를 평가하고 출시 후 30일 운영 계획을 실행한다
> - 첫 출시 이후의 다음 단계(두 번째 게임, 수익 다각화)를 숫자에 근거해 선택할 수 있다
>
> **선수 장**: 01~29 전체 (최소 04, 10, 11, 12, 21~24, 26~29) · **예상 시간**: 12주 (주 15~20시간 기준) · **코인 러시 진행**: 코인 러시는 완성된 예시로 쓰이고, 여러분의 게임이 새로 생깁니다

## 왜 필요한가

29장까지 오면서 여러분은 코인 러시를 따라 만들었습니다. 그런데 따라 만든 것과 **처음부터 혼자 결정하며 끝까지 내놓는 것**은 다른 능력입니다.

```
따라 만들기                               자기 게임
- 무엇을 만들지 이미 정해져 있음           - 장르·훅·범위를 스스로 정해야 함
- 막히면 다음 절에 답이 있음               - 막히면 컷할지 버틸지 스스로 판단
- 재미는 검증된 장르 공식                  - 재미가 없을 수 있음 → 버릴 용기 필요
- 스토어·마케팅은 예시 문안                - 내 게임의 문장을 내가 써야 함
- 끝이 정해져 있음                         - 끝을 스스로 정해야 함 (가장 어려움)
```

웹 개발 과정의 마지막 "개인 프로젝트 배포"가 이력서의 첫 줄이 되는 것처럼, 인디 게임 개발자의 첫 줄은 **출시한 게임**입니다. 이 장은 교과서 전체를 12주짜리 실행 계획으로 바꾸고, 각 주에 무엇을 만들어야 하는지, 언제 멈추고 판정해야 하는지, 무엇을 제출해 스스로 평가할지를 정합니다.

## 개념

### 캡스톤의 범위 — "3개월에 끝낼 수 있는 게임"

[29장](./29_scope-postmortem.md)의 출시 사다리에서 캡스톤은 **2단계(3개월 게임)** 입니다. 조건은 다음과 같습니다.

| 항목 | 기준 |
|---|---|
| 한 판 길이 | 5~15분 (세션 반복형) 또는 1~2시간 전체 플레이 |
| 코어 동사 | 1~2개 (예: 이동+회피, 배치+합성) |
| 콘텐츠 | 데이터(ScriptableObject)로 늘릴 수 있는 구조 — 적·무기·레벨을 코드 추가 없이 |
| 시스템 | 세이브 1종, 메타 진행 0~1개, 네트워크 없음 |
| 아트 | 기존 에셋 팩 계열 통일 + 핵심 비주얼(캡슐·주인공)만 제작/외주 |
| 플랫폼 | 하나 선택: **Steam** 또는 **모바일 1개 스토어** 또는 **itch.io(첫 출시가 1단계를 건너뛴 경우)** |
| 범위 기준 | 코인 러시 v1.0([21장](./21_core-loop-gdd.md), 24주 계획)의 **절반 이하**. 캡스톤 12주는 고정 업무를 빼면 기능에 쓸 수 있는 시간이 약 40 개발일(1일 = 3시간)뿐입니다(1단계 시간 검산) |

**플랫폼 선택과 일정 주의**: Steam 은 신규 파트너 대기 기간, 스토어 페이지·빌드 검토, Coming Soon 최소 2주 공개 규칙이 있어([26장](./26_steam-launch.md)) 12주 안에 출시하려면 **1주차에 Steamworks 가입·결제를 끝내야** 합니다. 가입이 늦어졌거나 정책상 기간이 맞지 않으면, 12주차 목표를 "Steam Coming Soon 공개 + itch.io 출시"로 바꾸고 Steam 출시는 그 뒤에 합니다. 출시 경험이라는 캡스톤의 목적은 똑같이 달성됩니다.

**Google Play 를 고르는 경우**: 2023년 11월 13일 이후 만든 **개인** 개발자 계정은 프로덕션 출시 전에 **테스터 12명 이상이 14일 연속 참여한 비공개 테스트**를 마치고 Play Console 에서 **프로덕션 액세스를 신청**해 심사(보통 7일 이내, 더 걸릴 수 있음)를 받아야 합니다. 일반 플레이테스트 10명으로는 충족되지 않고, 중간에 빠지는 테스터가 생기면 14일이 다시 필요할 수 있습니다. 그래서 12주 안에 출시하려면 **늦어도 7주차 초에 테스터 15~20명으로 비공개 테스트를 시작**해 9주차 말에 14일을 채우고, 10주차에 프로덕션 액세스를 신청합니다. 조직 계정이나 조건이 다른 계정은 Play Console 의 현재 요건을 확인하세요. 7주차까지 비공개 테스트 빌드를 올릴 수 없다면 12주차 목표를 "비공개 테스트 완료 + 프로덕션 액세스 신청"으로 조정합니다.

**교재의 다른 일정 예시와의 관계**: 21장 24주는 코인 러시 v1.0 전체 스코프의 개발 계획, 26장 D-180 표는 위시리스트를 충분히 모으는 Steam 표준 역산 일정, 이 장의 12주는 **더 작은 자기 게임으로 첫 출시를 끝내는 연습**입니다. 12주 안에서는 위시리스트 축적을 목표로 두지 않고 26장 표에서 가입·페이지 검토·빌드 검토만 가져옵니다([29장](./29_scope-postmortem.md) 출시 사다리 표).

### 평가 관점

루브릭은 "잘 만들었는가"만이 아니라 **"끝냈는가, 기준대로 판단했는가, 숫자를 남겼는가, 답이 없는 문제를 스스로 풀었는가"** 를 봅니다. 3개월 첫 게임의 성패는 판매량이 아니라 이것들로 평가하는 것이 다음 게임에 도움이 됩니다. 판매량은 기록하되 점수에 넣지 않습니다.

다만 두 가지를 분명히 구분합니다.

- **필수 통과 조건**: 실행 불가, 저장 손실, 결제 보상 오류는 총점이 아무리 높아도 **불통과**입니다. 플레이어의 돈과 시간을 잃게 하는 결함은 점수로 상쇄되지 않습니다.
- **교육 수료와 전업 전환은 다른 판단**입니다. 루브릭은 "첫 출시를 끝까지 해낼 수 있는가"를 판정합니다. "게임으로 생계를 꾸릴 수 있는가"는 이 루브릭으로 판정하지 않고, 29장 런웨이 기준과 실제 순수입 기록으로 따로 판단합니다(4단계 끝).

- **과제 B — 버그 진단 (9~11주차)**: 외부 테스트에서 나온 실제 버그, 또는 스터디원이 몰래 심은 버그 하나를 **답을 보지 않고** 진단합니다. 기록 형식: 재현 절차 → 가설 2개 이상 → 각 가설을 확인한 수단(로그·브레이크포인트·프로파일러·테스트) → 원인 → 수정 → 같은 버그를 다시 잡을 회귀 테스트나 재현 절차.

**수료 판정과 전업 판단의 분리**

| 구분 | 무엇을 판정하나 | 기준 |
|---|---|---|
| **캡스톤 수료** (이 교재의 교육 목표) | 혼자 게임 하나를 기준대로 판단하며 공개 출시까지 끝낼 수 있는가 | 필수 통과 조건 F1~F3 모두 통과 + 11개 영역 모두 2점 이상 + 3점 이상 영역 7개 이상 |
| **전업 전환 판단** (사업 결정) | 게임 수입으로 생활비와 다음 작품 제작비를 댈 수 있는가 | 이 루브릭으로 판정하지 않음. [29장](./29_scope-postmortem.md) 런웨이 기준(확정 수입만), 실제 정산된 순수입(장당 순수입 × 판매, 입금 기준), 출시 경험 수와 지표로 검증된 다음 기획을 함께 봄 |

루브릭에서 4점을 받아도 전업 근거가 되지 않고, 첫 게임 매출이 적어도 수료에는 영향이 없습니다.

**(e) 프로젝트 골격 자동 생성 에디터 스크립트**

매번 폴더를 손으로 만들지 않도록 1주차에 에디터 메뉴를 하나 만들어 둡니다([20장](./20_editor-tools.md)). 두 번째 게임에서도 그대로 씁니다.

`Assets/_CoinRush/Scripts/Editor/ProjectScaffold.cs`

```csharp
using UnityEditor;
using UnityEngine;

public static class ProjectScaffold
{
    // 루트 폴더 이름은 게임마다 바꾼다 (예: "_MyGame")
    private const string Root = "_CoinRush";

    private static readonly string[] Folders =
    {
        "Art", "Audio", "Audio/BGM", "Audio/SFX", "Data", "Data/Enemies", "Data/Weapons",
        "Data/Waves", "Fonts", "Materials", "Prefabs", "Scenes",
        "Scripts", "Scripts/Core", "Scripts/Gameplay", "Scripts/UI", "Scripts/Platform",
        "Scripts/Editor", "Settings"
    };

    [MenuItem("Tools/Capstone/Create Project Folders")]
    public static void CreateFolders()
    {
        EnsureFolder("Assets", Root);

        int created = 0;
        foreach (string relative in Folders)
        {
            string parent = "Assets/" + Root;
            foreach (string part in relative.Split('/'))
            {
                if (EnsureFolder(parent, part)) created++;
                parent = parent + "/" + part;
            }
        }

        AssetDatabase.Refresh();
        Debug.Log($"[Scaffold] 새 폴더 {created}개 생성 (이미 있는 폴더는 건너뜀)");
    }

    /// <summary>parent/name 폴더가 없으면 만들고 true, 이미 있으면 false.</summary>
    private static bool EnsureFolder(string parent, string name)
    {
        string path = parent + "/" + name;
        if (AssetDatabase.IsValidFolder(path)) return false;
        AssetDatabase.CreateFolder(parent, name);
        return true;
    }
}
```

1. 새 Unity 6 프로젝트(Universal 2D 템플릿)를 만들고 위 파일을 `Assets/_<게임명>/Scripts/Editor/` 에 둡니다(`Editor` 폴더 안이어야 빌드에서 제외됩니다).
2. 상단 메뉴 **Tools → Capstone → Create Project Folders** 를 실행합니다.
3. Console 에 생성 개수가 출력되고 Project 창에 폴더 트리가 생기면 성공입니다. 곧바로 Git 에 커밋하고 원격 저장소에 푸시합니다.

1. **1주차에 "완벽한 아이디어"를 찾느라 3주 소비** → 프로토타입 시간이 사라짐 → 1주차 금요일에 아이디어를 강제로 확정합니다. 틀렸다면 G1 이 알려줍니다.
2. **G1 전에 아트·UI 작업 시작** → 재미 없는 게임을 예쁘게 만듦 → 2주차까지는 그레이박스만. 아트는 G1 통과 후.
3. **게이트를 "나중에 한 번에" 판정** → 기준 없이 계속 진행 → 판정 기록 양식을 캘린더 알림과 함께 미리 만들어 둡니다.
4. **10주차 이후 콘텐츠 추가** → 새 콘텐츠가 새 버그를 만들어 출시 연기 → 동결 후 추가 아이디어는 출시 후 목록으로. FeatureCuts 로 반쯤 된 기능은 끕니다.
5. **Steam 일정 규칙을 11주차에 확인** → 대기 기간·검토·Coming Soon 2주 때문에 출시 불가 → 1주차에 가입, 7주차에 페이지 제출(스크린샷·1차 캡슐은 수직 슬라이스에서), 10주차에 빌드 검토 제출. 불가능하면 12주차 목표를 조정합니다.
6. **출시 직후 바로 두 번째 게임 착수** → 핫픽스·리뷰 대응 공백, 포스트모템 누락 → 30일 운영 계획을 끝내고 포스트모템을 쓴 뒤 시작합니다.

## 연습 문제

**1. ★☆☆** 자기 게임의 1주차 산출물 (a)~(d)를 코인 러시 예시 형식 그대로 작성하세요.

<details><summary>힌트·해설</summary>

가장 흔한 실패는 "핵심 재미 가설"이 검증 불가능한 문장인 경우입니다("재미있다" ✕). 관찰 가능한 행동으로 쓰세요: "테스터가 첫 사망 후 설명 없이 재시작 버튼을 누른다", "한 판에 선택을 고민하며 멈추는 순간이 3회 이상". 이 문장이 G1 판정 기준이 됩니다.

</details>

**2. ★★☆** 자기 게임 기준으로 12주 계획표와 시간 검산표를 다시 쓰되, 각 주의 작업을 3점 추정으로 계산해 개발 가용 시간(가용 − 계획·빌드·로그 − 마케팅)의 80% 를 넘는 주를 찾고 조정하세요.

<details><summary>힌트·해설</summary>

주 17시간에서 계획·빌드·로그 2시간과 마케팅 3시간을 먼저 빼면 개발 가용은 12시간(4 개발일)이고, 그 80% 인 9.5시간(약 3.2일)이 한 주에 계획할 수 있는 상한입니다. 흔히 하는 실수는 17시간 전체(5.7일)의 80% 인 4.5일을 상한으로 잡는 것인데, 그러면 마케팅·행정 시간이 버퍼를 잠식합니다. 넘는 주는 ① 작업을 앞뒤 주로 옮기거나 ② Should 를 Could 로 내리거나 ③ 범위를 줄입니다. "마지막 10% 묶음"(옵션·포커스·해상도·세이브 엣지)을 한 주에 몰지 않고 해당 시스템을 만드는 주에 나눴는지, 합계를 과소평가하지 않았는지 특히 확인하세요 — 29장 가상 포스트모템에서 일정 초과의 원인이었습니다.

</details>

**3. ★★☆** 루브릭 11개 영역 중 자기 약점이라고 예상되는 영역 3개를 고르고, 각 영역에서 3점을 받기 위해 12주 계획표의 어느 주에 무엇을 추가해야 하는지 적으세요.

<details><summary>힌트·해설</summary>

예: "행정·법이 약함 → 1주차에 세무사 상담 예약, 5주차에 SDK 목록표, 9주차에 처리방침 게시, 11주차에 라이선스 대장 대조". 약점 보완 작업도 추정표에 행으로 넣어야 실제로 실행됩니다. 계획표 밖의 "틈틈이"는 실행되지 않습니다.

</details>

**4. ★★★** 캡스톤을 실제로 12주 동안 수행하세요. 매주 주간 로그 5줄, 게이트 판정 기록 3장, 제출물 6종을 완성하고, 출시 30일 뒤 루브릭으로 자기 평가한 표와 "두 번째 게임 결정(A/B/C)"을 근거와 함께 작성하세요.

<details><summary>힌트·해설</summary>

진행 중 기준을 지키기 어려울 때를 대비해 **공개 약속**을 권장합니다: Discord·SNS 에 "12주 출시 챌린지"를 선언하고 매주 금요일 로그를 게시하면 마케팅 콘텐츠도 됩니다. Kill 판정이 나도 캡스톤은 실패가 아닙니다 — 그 시점까지의 포스트모템을 쓰고 새 기획으로 3주차부터 재시작하면 됩니다. 평가는 판매량이 아니라 루브릭 기준입니다.

</details>

## 셀프 체크

**1.** 캡스톤에서 게이트를 2·6·10주차에 두는 이유를 각각 설명해보세요.

<details><summary>모범 답안</summary>

2주차는 그레이박스만으로 재미를 판정해 아트·시스템 투자 전에 방향을 바꿀 수 있는 가장 싼 시점입니다. 6주차는 코어 시스템이 갖춰져 최종 품질의 짧은 구간으로 외부 반응(영상·테스트)을 볼 수 있고, 남은 기간에 범위를 조정할 여유가 있는 시점입니다. 10주차는 출시 준비(최적화·스토어·행정·버그)에 최소 2주가 필요하므로 새 콘텐츠를 멈추는 마지막 시점입니다.

</details>

**2.** Steam 을 캡스톤 플랫폼으로 고를 때 1주차에 해야 하는 일과 그 이유는?

<details><summary>모범 답안</summary>

Steamworks 가입과 Steam Direct 결제, 은행·세금 정보 입력을 1주차에 끝내야 합니다. 신규 파트너 대기 기간, 스토어 페이지와 빌드 검토 시간(반려 시 재제출 포함), 출시 전 Coming Soon 최소 공개 기간이 있어 늦게 시작하면 12주 안에 출시할 수 없기 때문입니다. 그래서 1주차 가입 → 7주차 페이지 검토 제출(수직 슬라이스 스크린샷·1차 캡슐) → 10주차 빌드 검토 제출 순서로 역산합니다. 일정이 맞지 않으면 목표를 Coming Soon 공개 + itch.io 출시로 조정합니다.

</details>

**3.** 루브릭에 판매량을 점수로 넣지 않는 이유는?

<details><summary>모범 답안</summary>

첫 3개월 게임의 판매량은 장르·시기·운 등 통제하기 어려운 요인의 영향이 크고, 이 단계의 목적은 끝내는 능력·기준에 따른 판단·숫자 기록이라는 반복 가능한 역량을 기르는 것이기 때문입니다. 판매량은 포스트모템에 기록해 다음 결정의 근거로 쓰지만, 평가 점수로 쓰면 통제 가능한 개선 과제가 흐려집니다. 같은 이유로 루브릭은 전업 전환의 근거도 아닙니다. 생계 가능성은 런웨이(확정 수입만)와 실제 정산된 순수입으로 따로 판단합니다. 반대로 점수와 무관하게 실행 불가·저장 손실·결제 보상 오류가 있으면 불통과인데, 플레이어의 시간과 돈을 잃게 하는 결함은 다른 영역의 점수로 상쇄되지 않기 때문입니다.

</details>

**4.** 출시 후 30일 동안 새 대형 기능을 시작하지 않는 이유는?

<details><summary>모범 답안</summary>

이 기간에는 크래시·해상도 같은 치명적 문제의 핫픽스와 리뷰 대응이 판매·평가에 가장 큰 영향을 주고, 실제 플레이어의 데이터와 요청을 모아야 출시 후 목록의 우선순위를 올바르게 정할 수 있기 때문입니다. 대형 기능은 새 버그로 대응 여력을 빼앗습니다.

</details>

**5.** 두 번째 게임을 "같은 게임 확장 / 같은 장르 새 게임 / 다른 장르" 중에서 고를 때 각각 필요한 근거는?

<details><summary>모범 답안</summary>

확장은 긍정 리뷰 비율과 긴 플레이 시간, 콘텐츠 추가 요청이 많을 때 택합니다. 같은 장르 새 게임은 장르 반응은 확인됐지만 첫 게임의 훅이나 범위에 구조적 한계가 있었을 때 택합니다. 다른 장르는 장르 시장 신호가 약했을 때 택하되 짧은 프로토타입으로 훅부터 다시 검증합니다. 어느 경우든 킬 기준 문서로 시작합니다.

</details>

## 핵심 요약

- 캡스톤은 출시 사다리 2단계: 5~15분 세션, 동사 1~2개, 데이터로 늘리는 콘텐츠, 네트워크 없음, 플랫폼 하나.
- 12주 = 기획·프로토(1~2) → 코어(3~6) → 콘텐츠·폴리싱(7~10) → 출시(11~12), 게이트는 2·6·10주차.
- 게이트 기준은 1주차 킬 기준 문서에 미리 적고, 판정 기록은 다음 날 다시 읽고 확정합니다.
- Steam 을 고르면 1주차 가입·7주차 페이지 제출·10주차 빌드 검토 제출, 신규 개인 Google Play 계정이면 7주차 비공개 테스트 시작(12명 이상·14일 연속)이 필수이며, 맞지 않으면 목표를 조정합니다.
- 버퍼는 매주 개발 가용의 20% 를 비워 잔고로 쌓습니다(29장의 "추정 + 25%"와 같은 규칙). 마케팅·계획 시간은 먼저 공제합니다.
- 제출물 6종(기획서, 웨이브·밸런스 표, 테스트 리포트, 스토어 페이지, 출시 체크리스트, 포스트모템)이 게임과 함께 남습니다.
- 실행 불가·저장 손실·결제 보상 오류는 총점과 무관하게 불통과입니다. 루브릭은 출시·판단·숫자·독립 수행을 평가하고, 구조는 특정 기법 사용이 아니라 변경 비용·검증 가능성으로 봅니다. 판매량은 기록만 합니다.
- 캡스톤 수료는 "첫 출시를 끝낼 수 있다"의 판정이고, 전업 전환은 런웨이·실제 순수입으로 따로 판단합니다.
- 출시 후 30일은 핫픽스·리뷰·데이터 수집·포스트모템에 쓰고, 두 번째 게임과 수익 다각화는 그 숫자로 결정합니다.
